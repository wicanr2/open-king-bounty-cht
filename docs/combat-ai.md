# 戰鬥電腦 AI 邏輯(現況分析)

本文整理 `src/game.c`(AI 決策本體)與 `src/play.c`(狀態管理、動作結算)中,電腦對手(以及「失控」單位)在戰鬥畫面實際的決策邏輯。目的是為 GitHub issue #9「進化版 AI」提供現況基準——**只描述目前程式碼實際做什麼,不補original King's Bounty 的行為**。看不懂或推不出結論的地方一律標「待確認」。

涉及檔案:`src/game.c`(`ai_pick_target`、`ai_unit_think`、`combat_loop`、`hit_unit`、`move_unit`、`fly_unit`、`unit_try_shoot`/`unit_ranged_damage`、`pick_target`)、`src/play.c`(`next_turn`、`next_unit`、`reset_turn`、`reset_match`、`unit_under_control`、`units_are_friendly`、`unit_touching`、`unit_surrounded`、`unit_move_offset`/`unit_fly_offset`/`unit_closest_offset`、`deal_damage`、`unit_hit_unit`、`unit_ranged_shot`、`compact_units`)、`src/bounty.h`(`KBunit`、`KBtroop`、`KBcombat` 結構)。

## 1. 總覽:一場戰鬥怎麼跑

- 戰場是 `CLEVEL_W × CLEVEL_H = 6×5` 格(`src/bounty.h:249-250`),每邊最多 `MAX_UNITS = 5` 個兵種疊(`bounty.h:253`)。
- `KBcombat` 用 `side`(0=玩家、1=電腦/怪物)+ `unit_id` 指向「目前輪到哪一個單位」,`phase` 記錄本回合是第幾輪掃描(見下)(`bounty.h:281-300`)。
- 對戰一開始 `combat` 結構整個 zero-init(`run_combat`,`game.c:3572`:`KBcombat combat = { 0 };`),而且程式碼裡**唯一**對 `side` 賦值的地方只有 `next_turn` 的切換(`play.c:1300`)。也就是說:**永遠是玩家(side 0)先手**,程式中沒有依單位速度/技能決定先攻的邏輯(不同於一般直覺印象的「速度快先攻」,這裡就是「一方全部單位動完,換下一方」)。
- 主迴圈在 `combat_loop`(`game.c:6154`)。每個畫面 tick 收到 `COMBAT_SYN_EVENT` 時,單位動畫幀數跑滿(`frame>3`)就觸發一次行動判斷(`game.c:6297-6303`):
  ```c
  if (auto_battle || combat->side == 1 || combat->units[combat->side][combat->unit_id].out_of_control)
      pass = ai_unit_think(combat);
  ```
  也就是 `ai_unit_think` 會在三種情況下被呼叫:①真正的電腦對手(`side==1`)、②任何一方「失控」(`out_of_control`)的單位(見第 5 節)、③玩家開啟「Auto-combat」除錯/輔助開關時(`auto_battle`,`game.c:45`、`5062-5063`,熱鍵可切換),此時連玩家自己的部隊也交給同一套 AI 邏輯操作。三者共用**同一份**決策程式,沒有分開寫。
- 玩家輸入在 AI/失控回合會被丟棄(`game.c:6215-6220`),包含 `USE_MAGIC` 熱鍵——**AI 完全不會呼叫 `choose_spell`**(唯一呼叫點在 `game.c:6276` 與 `6555`,兩處都只在人類手動按鍵路徑上),詳見第 6 節。
- 單位動完後(`pass` 或 `u->acted` 為真),先檢查勝敗(`test_defeat`/`test_victory`,`play.c:1071-1085`),沒分勝負就呼叫 `next_unit`/`next_turn` 推進(`game.c:6335-6338`):
  - `next_unit`(`play.c:1309-1329`)在**同一個 `side`** 的陣列裡,從 `unit_id+1` 往後找一個「還活著且未 `acted`」的單位;找不到就 `phase++`,再從頭(`i=0`)掃一次同一個 `side`。兩輪都找不到才回傳 `-1`。
  - 回傳 `-1` 時呼叫 `next_turn`(`play.c:1292-1306`):`turn++`、`reset_turn`(見第 5 節)、然後在**尚未切換前的舊 `side`** 陣列裡找第一個活著的索引存入 `unit_id`,最後才把 `side` 反轉(`1 - war->side`)。
    - 待確認/觀察:這裡是搜尋「舊 side」的陣列來決定新 side 要從哪個 `unit_id` 開始,乍看像是找錯陣列;但因為 `compact_units`(`play.c:1389-1430`)每次死亡後都會把兩邊的存活單位往前壓縮(不留洞),兩邊「第一個存活索引」實務上恆為 0,所以目前寫法功能上等同「新回合固定從 unit_id=0 開始」,不會造成明顯錯誤,但寫法本身容易誤讀,列為待確認/建議未來加註解或直接改成掃新 side。
  - 這代表**一整方的單位會依序全部行動完(含最多 2 個 phase 的等待重掃),才輪到另一方**,不是逐一交替單位。
- `MAX_PHASES`(`bounty.h:255`,值為 2)只是描述性常數,程式裡**沒有任何地方拿它跟 `phase` 比較**——2 個 phase 的上限是由 `next_unit` 只呼叫一次 `phase++`(`play.c:1319`)這個結構本身保證的,不是靠常數檢查。

## 2. 單位決策流程(`ai_unit_think`,`game.c:5974-6066`)

`ai_unit_think` 每次只處理「目前輪到的這一個單位」,判斷順序完全是**固定的 if 序列**,不是評分/效用制;一旦某個分支「動了」(`acted=1`),後面分支就不會再檢查。順序如下(對應行號):

```
① close_target = ai_pick_target(combat, nearby=1)      // game.c:5979,永遠先算一次「近戰目標」
② 若 u->frozen                                          → 整回合被凍結,acted=1,結束(5984-5990)
③ 若 u->shots > 0 且 close_target == -1                 → 嘗試遠程射擊(5993-6010)
④ 若 u->flights > 0 且 close_target == -1 且尚未 acted   → 嘗試飛行(6013-6032)
⑤ 若 u->shots == 0 且尚未 acted                          → 嘗試移動(含撞人變成近戰攻擊)(6035-6056)
⑥ 都不成立                                              → 待命 unit_try_wait(6059-6063)
```

逐點細節:

- **① 永遠先問「有沒有貼身的敵人」**:`close_target` 只算一次,之後③④⑤都直接讀這個變數,不會重算(除非③④裡另外呼叫 `ai_pick_target(combat,0)` 算「遠方目標」)。「貼身」= `unit_touching`(8 方向,含斜角,`play.c:1332-1346`)。
- **② 凍結最優先**:只要 `u->frozen` 為真,不管有沒有貼身敵人、有沒有子彈,直接跳過所有動作,`combat_log` 印「%s 被凍結」,回合結束(`game.c:5984-5990`)。
- **③ 射擊條件是「沒有貼身敵人」而非「沒被包圍」**:程式碼用 `close_target == -1` 當「可以射擊」的閘門(`game.c:5996`),語意上等同「附近沒有敵人貼身」;但這跟人類手動射擊用的 `unit_surrounded`(`play.c:1349-1360`,`game.c:5857` 呼叫)不是同一個函式呼叫,只是效果相近(兩者都是「周圍有沒有敵對單位貼身」,但 `ai_pick_target(nearby=1)` 在單位失控時也會把「己方」算進候選,細節見第 3 節)。若 `close_target==-1`,才呼叫 `ai_pick_target(combat,0)` 找遠方目標,找得到就直接呼叫 `unit_ranged_damage`(`game.c:6003`,即 `deal_damage` 的射擊分支,見第 4 節)——**AI 射擊完全不檢查彈藥用量以外的任何戰術條件**(沒有「保留子彈」「優先集火」等邏輯)。
- **④ 飛行只在「沒有貼身敵人」且射擊沒有發生時才嘗試**:呼叫 `unit_fly_offset` 算出往遠方目標貼近的一格(`play.c:1729-1762`,原理見第 4 節),`nx/ny` 若跟原地相同代表飛不過去(印 debug 訊息,`game.c:6026`),就會落到⑤的移動分支(因為 `acted` 仍是 0)。
  - **待確認/風險**:`game.c:6016-6018` 在呼叫 `ai_pick_target(combat,0)` 後,**沒有檢查回傳值是否為 `-1`** 就直接把它丟給 `unit_fly_offset`(`unit_move_offset` 在⑤也一樣沒檢查,`game.c:6043`)。若 `far_target==-1`,`UID_AS_ID(-1)` 會算出 `-2`,存取 `war->units[side][-2]` 屬於越界。經檢視,combat 每個動作後都會先跑 `test_defeat`/`test_victory` 才會繼續下一個單位(`game.c:6323-6331`),理論上輪到某單位行動時對方一定還有活著的單位,`ai_pick_target(0)` 幾乎不可能真的回傳 `-1`——但程式碼本身確實沒有防呆,是否存在能觸發的邊界情況待確認,建議日後補上 `if (far_target != -1)` 防呆。
- **⑤ 移動與「撞人即攻擊」共用同一個函式**:`unit_move_offset` 算出朝目標貼近的一步(`play.c:1710-1726`,原理見第 4 節);`move_unit`(`game.c:3511-3550`)實際執行時,如果目的地格已經站著單位,不管是敵是友,都會呼叫 `hit_unit`(見第 4 節),除非雙方都是「正常(非失控)的己方單位」才會擋下(`game.c:3532-3535`)。也就是說,AI 的「移動」分支其實同時涵蓋了「移動」跟「近戰攻擊」兩種結果,由 `ai_pick_target` 選出的目標位置決定。
- **⑥ 待命是保底分支**,只要前面都沒有動作(沒被凍結、沒射擊、沒飛成、也沒移動/攻擊成功——例如貼身有敵人但 `unit_move_offset` 算不出可走的格子),就呼叫 `unit_try_wait`(`game.c:5806-5815`)。這個函式本身跟「phase」制度連動:只有 `war->phase` 非 0(第二輪掃描)時才會把 `acted` 設成 1(`game.c:5810`);換句話說,**AI 在第一輪掃描時「待命」不會真的耗掉行動**,理論上還能在第二輪(phase 1)被 `next_unit` 重新掃到、再嘗試一次(但因為場面狀態通常沒變,AI 邏輯是決定性的,重掃多半得到一樣結果)。

## 3. 目標選擇(`ai_pick_target`,`game.c:5925-5972`)

```c
int ai_pick_target(KBcombat *combat, int nearby) {
    int under_control = !combat->units[combat->side][combat->unit_id].out_of_control;
    int far = 1 - nearby;
    ...
    for (j = 0; j < MAX_SIDES; j++) {       // side 0 → 1
    for (i = 0; i < MAX_UNITS; i++) {       // 每邊 slot 0 → 4
        ...掃描...
    }}
}
```

### 3.1 候選過濾(依序)

1. `!u->count` → 跳過(已死亡/空位)。
2. 是自己 → 跳過。
3. **若自己是「正常控制」單位(`under_control` 為真),同一邊的單位一律跳過**(`game.c:5939`)——也就是說,正常單位**永遠只會挑對方陣營**當目標,不可能誤傷友軍。
4. **若自己是「失控」單位(`out_of_control`),第 3 點的跳過條件不成立,己方單位也會被列入候選**(`under_control` 為假時,整個條件式為假,不 `continue`)——這是失控單位可能打到自己人的直接原因。
5. `nearby` 模式下,若目標沒有跟自己「貼身」(`unit_touching`)就跳過;`far` 模式(`nearby=0`)不做距離篩選,理論上場上所有非己方(或失控時含己方)存活單位都算候選。

### 3.2 優先序(有沒有「打薄弱/優先射手」邏輯——如實記錄現況)

比較邏輯只在**已經有一個候選(`pick != -1`)**時才會跑,規則是「除非符合跳過條件,否則直接覆蓋成目前掃到的這個」——這代表它**不是排序,而是線性掃描 + 覆蓋**,行為細節如下:

- **遠方目標(`far=1`,對應射擊/飛行決策)**:
  - 若目前選到的 (`picked`) 還有 `shots`(彈藥>0),而新掃到的候選沒有彈藥 → 跳過(保留原本會射擊的目標)(`game.c:5947-5949`)。
  - 除此之外——包含「新候選也有彈藥」的情況——**血量比較整段被跳過**(`game.c:5952`:`if (!far || (!u->shots))`,`far=1` 時只有候選「沒有彈藥」才會做血量比較),所以只要新候選有彈藥,就會**無條件覆蓋**目前的選擇。
  - **實際效果**:如果場上有多個仍有彈藥的敵方單位,最終選到的會是**掃描順序中最後一個「有彈藥」的單位**(side 0 slot 0→4,再 side 1 slot 0→4),**跟血量、彈藥剩餘量、兵種強弱完全無關**。只有當場上**沒有任何**敵方單位還有彈藥時,才會退回用 `troops[].hit_points`(兵種最大血量,不是目前殘存數量)比較,挑數值較低者;打平的話一樣是後掃到的蓋過先掃到的。
  - **結論:issue #9 想強化的「優先打薄弱/遠程/施法單位」,目前只有「有彈藥的目標優先於沒彈藥的」這一條粗略規則,而且連這條規則本身也不是嚴格排序(多個有彈藥目標時退化成「最後一個」),沒有依血量、剩餘彈藥量或兵種特性(如魔法、施法者)做真正的加權比較。**
- **貼身目標(`nearby=1`,`far=0`)**:射手優先的判斷區塊(`if (far)`)整段跳過,直接做血量比較(`game.c:5952-5955`):新候選 `hit_points` 大於目前選中者就跳過,否則覆蓋。也就是**貼身目標選擇確實會偏好「兵種血量較低」的敵人**(如優先打農民而非龍),但打平(同血量)一樣是後掃到的蓋過先掃到的,且比較基準是**兵種上限血量**,不是「殘存數量×血量」或「這次能不能斬殺」這種更貼近實戰的指標。
- **完全沒有隨機性**:整個函式沒有任何 `rand()`/`KB_rand()` 呼叫——同一個盤面狀態,AI 永遠選出同一個目標,可被預判。

### 3.3 與人類版 `pick_target`(`game.c:5710-5804`)的差異

`pick_target` 是給玩家用的:只負責畫游標、讓玩家用方向鍵移動選取範圍,再依 `filter` 參數(1=空地、3=己方非失控、4/5=敵方或失控單位)判斷該格是否「可選」,**完全沒有自動挑選邏輯**——選誰、選哪一格都是玩家自己決定。`ai_pick_target` 則是純程式判斷,兩者除了都要分辨敵我/失控狀態外沒有共用程式碼。

## 4. 各動作的觸發條件與後果

| 動作 | 觸發函式 | 前置條件 | 後果 |
|---|---|---|---|
| 移動 | `unit_move_offset`(`play.c:1710`)+ `move_unit`(`game.c:3511`) | `u->shots==0` 且尚未行動;目的格非障礙、非邊界 | 消耗 1 點 `moves`;`moves` 歸零則 `acted=1`(`game.c:3546-3547`) |
| 近戰攻擊 | 同上,`move_unit` 偵測到目的格有單位 | 目的格站著敵人,或站著「失控」單位(含己方) | 呼叫 `hit_unit`(見下),`u->acted` 直接設為 1(不消耗 `moves`) |
| 射擊 | `unit_ranged_damage`(`game.c:5904`)→ `unit_ranged_shot`(`play.c:1590`)→ `deal_damage`(`play.c:1433`, `is_ranged=1`) | `u->shots>0` 且 `close_target==-1` | 消耗 1 點 `shots`(`play.c:1473`);傷害算完後 `acted=1`(`game.c:5919`);**不會**觸發反擊(見下) |
| 飛行 | `unit_fly_offset`(`play.c:1729`)+ `fly_unit`(`game.c:3552`) | `u->flights>0` 且 `close_target==-1` 且尚未行動 | 消耗 1 點 `flights`;歸零則 `acted=1`(`game.c:3561`) |
| 待命/略過 | `unit_try_wait`(`game.c:5806`) | 前述動作都沒有發生 | 只有 `war->phase!=0` 才會 `acted=1`,否則本回合仍可能在第二輪被重新掃到 |

### 4.1 移動的「往哪走一步」怎麼算(`unit_closest_offset`,`play.c:1655-1707`)

這不是路徑規劃(BFS/A*),而是**貪心的單步啟發式**:只看目前(或飛行時,目標)位置周圍 3×3(扣掉不合法格)共 8 格,用曼哈頓距離(`calc_distance` 巨集,`play.c:1645`,`abs(dx)+abs(dy)`,程式裡原本有歐幾里得距離的 `isqrt32` 實作但被 `#undef` 掉沒用到,`play.c:1611-1644`)挑一格能讓自己離目標最近的鄰接格;被障礙(`omap`)或其他單位(`umap`,目標格本身除外)佔用的格子距離視為最大值(等於直接排除)。**如果 8 格都不會更靠近目標(例如被牆整片擋住,需要繞路)`ox/oy` 回傳 0,0,單位就完全不會動,直接落到待命分支**——這代表 AI 沒有繞障礙物的能力,可能在複雜地形卡住不動。

### 4.2 近戰攻擊與反擊(`hit_unit`,`game.c:3477-3508`)

```c
kills = unit_hit_unit(a, t);          // 攻擊方打目標
if (t->retaliated == 0) {
    t->retaliated = 1;
    kills = unit_hit_unit(t, a);      // 目標立即反擊(僅一次)
}
```
- `unit_hit_unit` 底層都是呼叫 `deal_damage(..., retaliation=1)`(`play.c:1584`)。
- `t->retaliated` 每回合開始(`reset_turn`,`play.c:1183`)重置為 0,所以**每個單位每整輪(自己的回合)最多被反擊觸發一次**,不是每次挨打都能反擊——如果同一輪內被打第二次(理論上一個單位一輪只行動一次,但被多個敵人先後攻擊時可能發生),第二次就不會再反擊。
- `deal_damage` 本身也寫了一段「自動反擊」邏輯(`play.c:1565-1570`:`if (!retaliation) { ... deal_damage(遞迴,retaliation=1) ... }`),但**檢視所有呼叫點後確認這段是死碼**:`unit_hit_unit`(近戰)、`unit_ranged_shot`(射擊,`is_ranged` 分支內會把 `retaliation` 強制設為 1,`play.c:1471-1472`)、以及另外兩處直接呼叫(`play.c:1858` 法術傷害、`game.c:4094`/`6994`)全部都是固定傳入 `retaliation=1`,實際的反擊全部是靠 `game.c` 的 `hit_unit` 手動呼叫兩次 `unit_hit_unit` 做到的。**這條規則對玩家、AI 一視同仁,不是 AI 特有行為。**

### 4.3 射擊為何不觸發反擊

`unit_ranged_damage`(不管是 AI 呼叫`game.c:6003`,或人類點擊射擊`game.c:6247`/`unit_try_shoot`路徑`game.c:5879`)**從頭到尾都沒有呼叫 `hit_unit`**,只呼叫 `unit_ranged_shot`。因為「反擊」這件事完全是 `hit_unit` 裡手動寫的兩段式攻擊,射擊路徑繞過了 `hit_unit`,自然沒有反擊——這是遊戲規則層級的行為(射擊不挨反擊),同樣對雙方一視同仁。

## 5. 狀態對 AI 的影響

- **`frozen`(凍結)**:見第 2 節,優先度最高,凍結時整回合什麼都不做。解除時機在 `reset_turn`,但**只有 `war->side==1` 時才解凍**(`play.c:1190-1192`:`if (war->side == 1) { war->units[j][i].frozen = 0; ... }`)——也就是凍結只在「AI 這一整方要開始行動前」被清除,若凍結法術是打在玩家單位上,玩家單位要撐到「切到 AI 那一側」的 `next_turn` 才會解凍,待確認這與凍結法術實際使用情境(通常玩家對敵方施放)是否有相依性影響,本次未深入法術系統。
- **`out_of_control`(失控)**:
  - **判定依據是「統率力(leadership)夠不夠」而非士氣**:`unit_under_control`(`play.c:1363-1368`)——若該側沒有 `hero`(掛在 `war->heroes[side]`,怪物/城堡守軍固定是 `NULL`,`play.c:1126`、`1145`),永遠回傳「受控」;有 hero 的話(通常是玩家),用 `army_leadership(hero, troop_id) > 0` 判斷,亦即該兵種佔用的統率力超過英雄自身統率上限時才會失控。
  - **只有玩家(側 0)才會真的失控**:`prepare_units_foe`/`prepare_units_castle` 建立敵方單位時直接寫死 `out_of_control = 0`(`play.c:1119`、`1138`),敵方/城堡守軍永遠受 AI 正常控制,不會出現「敵方失控打自己人」的情況。
  - **失控單位由玩家發起攻擊時的行為和真正的 AI 側完全共用同一份 `ai_unit_think`**(見第 1 節的三種觸發條件),而且第 3 節提到,失控單位在挑目標時會把**己方(含自己以外的友軍)也算進候選**,理論上真的可能打到自己人。
  - **士氣(`troop_morale`,`play.c:613-628`)完全不影響是否失控,只影響傷害倍率**(`deal_damage`,`play.c:1493-1503`:低士氣傷害 ÷2,高士氣傷害 ×1.5),而且**只有「有 hero 且該單位受控」的一方攻擊時才會套用**——也就是說,怪物/敵方陣營(沒有 hero)攻擊永遠不會有士氣加成/懲罰,只有玩家自己的部隊(受控狀態)攻擊時才吃士氣修正。
- **`moves`/`shots`/`flights` 上限**:
  - `moves`(每回合重置為 `troops[].move_rate`)與 `flights`(有 `ABIL_FLY` 才重置為 2,否則 0)都是**每一整輪(`reset_turn`)重新填滿**(`play.c:1185-1188`)。
  - **`shots`(彈藥)只在整場戰鬥開始時設定一次**(`reset_match` → `reset_turn` 呼叫鏈之外,`play.c:1254`:`u->shots = troops[u->troop_id].ranged_ammo;`,只在 `reset_match` 執行,`reset_turn` 完全沒有碰 `shots`),**整場戰鬥打完才會重置,不會每輪回滿**——這代表遠程單位的彈藥是消耗品,打光了整場戰鬥就只能改用移動/近戰(`ai_unit_think` 的③射擊分支要求 `u->shots>0` 才會進入,彈藥用完後行為會自動退化成⑤移動分支)。

## 6. 現況評估(給 issue #9「進化版 AI」參考,本次不實作)

**摘要**:目前 AI 是一套完全決定性、單步貪心、無戰術層的規則機。決策順序固定(凍結 → 射擊 → 飛行 → 移動/近戰 → 待命),目標選擇對「貼身敵人」有基本的「打弱不打強」邏輯(比 `hit_points`),但對「遠方/有彈藥的目標」只是線性掃描覆蓋,退化成「最後一個有彈藥的」而非真正排序;移動是不繞障礙物的單步貪心;完全沒有法術、集火、保留戰力、風險評估等戰術行為;沒有任何隨機性,同盤面永遠同結果,容易被預判。

具體弱點(供 P4 強化參考):

1. **遠方目標選擇不是「挑弱」而是「挑最後一個有彈藥的」**(`game.c:5947-5955`)——多個敵方射手同時存在時,選誰純粹看陣列掃描順序,沒有依血量、剩餘彈藥、兵種價值排序。
2. **貼身目標選擇只看兵種「上限血量」,不看殘存數量或這一擊能否斬殺**——沒有「集火補刀」邏輯,也不會辨識「這隻只剩 1 隻,一擊可團滅」這種高價值目標。
3. **移動是不會繞路的單步貪心**(`unit_closest_offset`,`play.c:1655`)——遇到需要繞過障礙物才能接近目標的地形,AI 會直接卡住待命,不會嘗試其他路線。
4. **完全沒有法術 AI**——`choose_spell` 只掛在人類按鍵路徑上(`game.c:6276`、`6555`),AI/失控/自動戰鬥都不會施法,即使該方英雄有法力與可用法術。
5. **不辨識兵種特殊能力**——選目標時沒有讀取 `ABIL_IMMUNE`/`ABIL_MAGIC`/`ABIL_UNDEAD` 等旗標(`bounty.h:195-202`),不會避開「打了沒用」的目標(如對免疫魔法的目標仍可能被沒意義地標成優先),也不會利用己方特殊能力(如優先讓吸血/回血單位打殘存量多的目標)。
6. **零隨機性**——沒有 `rand()` 介入目標選擇,行為完全可預判,對重複遊玩的玩家而言戰術上沒有「意外」。
7. **`ai_pick_target(0)` 回傳 `-1` 時,飛行/移動分支沒有防呆**(`game.c:6016-6018`、`6040-6043`)就直接送進 `UID_AS_SIDE/UID_AS_ID` 巨集,存在理論上的越界風險(見第 2 節「待確認」),雖然目前呼叫路徑下很難觸發,仍建議之後補防呆。

### 待確認清單(彙整)

- `next_turn`(`play.c:1292`)在切換 side 前搜尋「舊 side」陣列來決定新 `unit_id` 的寫法,是否為刻意設計或純粹巧合(靠 `compact_units` 保證存活單位靠前才不出錯)——本次判斷為「功能上安全但寫法易誤讀」,未完全確定原作意圖。
- `ai_unit_think` 的射擊放行條件用 `close_target==-1`(來自 `ai_pick_target(1)`)而非直接呼叫 `unit_surrounded`——效果上判斷為等價(都是問「周圍有沒有可打的目標」),但兩者在失控單位語意下是否 100% 等價未逐案窮舉驗證。
- `ai_pick_target(combat,0)` 是否存在真的會回傳 `-1` 的可達路徑(進而讓第 2 節提到的越界風險成真)——本次僅靜態推論「幾乎不可能」,未做動態測試驗證。
- `frozen` 只在 `war->side==1` 才解除的時機,與施法方/目標方的對應關係(是否總是符合玩家對敵方施放凍結的預期)——本次未深入法術施放/生效的呼叫鏈,列為待確認。

## 進化版 AI(opt_ai_mode = 1)

延續第 6 節列出的弱點,issue #9 P4 實作了一套進化版目標選擇與單位決策(`ai_pick_target_evolved`/`ai_unit_think_evolved`,`src/game.c`),接上既有的 `opt_ai_mode` 開關。

**開啟方式**:戰鬥畫面按 F12 → `p`(遊戲調整設定選單)→ 戰鬥 AI 模式 → 切到「進化版」。設定隨存檔持久,原版仍是預設值。

### 與原版的兩個具體差異

**1. 目標選擇:從「打最弱」改成「打威脅最高」**

原版 `ai_pick_target` 在貼身模式(`nearby=1`)一律比較兵種上限血量,挑最低的那個(第 3 節已述);遠方模式則退化成「掃描順序中最後一個還有彈藥的」,兩者都跟「這個目標有多危險」無關。

進化版改成一套加權計分,分數最高者出線:

```
score = 0
if (該敵人本回合還有子彈 且 兵種本身有遠程彈藥上限) score += 1000   // 先解決敵方射手
score += 兵種 skill_level * 20                                    // 偏好高階兵種
score += 兵種 melee_max + ranged_max                              // 偏好高傷單位
if (貼身模式 且 該敵人本回合已反擊過)          score += 30         // 打了不會再挨還手
```

`+1000` 的權重刻意設得遠高於其他項,確保「還有子彈的敵方射手」永遠排在最前面,不會被兵種強度或血量蓋過。

離線單元測試(`ai_pick_target_evolved` 對 `ai_pick_target` 的差異對照,見下方「驗證」)實測結果:

- **貼身混戰(nearby=1)**,場上同時有「農夫(低血量、無射擊)」與「弓箭手(有子彈)」都貼身時:原版挑血量最低的農夫,進化版挑弓箭手(命中 +1000 規則)——這是原版「打弱不打強」與進化版「先拔釘子戶」差異最直接的場景。
- **遠方目標(nearby=0)、兩者都沒有子彈**,一隻低階(農夫,skill_level 1)一隻高階(武士,skill_level 5):原版仍挑血量低的農夫,進化版挑高階、高傷的武士——結果不受兩者在敵方陣列中的掃描順序影響(交換順序測試過,兩版本各自結果一致)。
- 附帶發現:原版遠方模式(`nearby=0`)在候選中「只有一個目標當下還有子彈」時,其實已經會優先選中該射手(第 3 節提到的「保留會射擊的目標」規則在只有一名射手時剛好生效),因此「農夫 vs 有子彈的弓箭手、都在遠方」這個組合下原版與進化版選的都是弓箭手,沒有觀察到差異——真正能看出「打最弱 vs 打威脅最高」差異的是貼身混戰與「兩者皆無子彈但兵種強度不同」這兩種場景。

**2. 射手被貼身處理:從空等改成近戰反擊**

原版射手(`u->shots>0`)一旦被敵人貼身(`close_target != -1`),就不會進入任何行動分支,直接落到 `unit_try_wait` 待命,白白浪費一回合火力。進化版新增一段:射手被貼身時,改用 `unit_move_offset` 朝貼身目標移動/近戰攻擊,不再空等。

### 設計取捨

進化版只在玩家於 F12 選單主動開啟時生效;原版邏輯(含其既有的弱點與怪異行為)完全不變,仍是預設體驗,不影響尚未接觸這個選項的既有玩家。
